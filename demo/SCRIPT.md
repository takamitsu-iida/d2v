# d2v デモ 発表者台本

> **想定時間**: 5〜6 分
> **推奨形式**: `demo.py` playback（Act 1 のみ live 切り替え可）
> **コマンド一覧** (手元メモ):
> ```
> uv run python demo.py          # 全シーン通し
> uv run python demo.py --scene 1  --open
> uv run python demo.py --scene 2  --open
> uv run python demo.py --scene 3  --open
> uv run python demo.py --scene 4
> uv run python demo.py --scene 5  --open
> uv run python demo.py --live     # Act 1 だけ本物の LLM
> ```

---

## Opening（〜30 秒）

> 「ネットワーク設計書を YAML で書いたら、構成図は自動で作りたい。
> 作った図の問題点は AI に指摘してほしい。
> 設計変更の影響範囲はワンコマンドで把握したい。
> ——それを全部やるのが d2v です。」

* 端末を画面に映し、エディタは閉じておく。
* フォントサイズ: 20pt 以上（後列から読める大きさ）。

---

## Act 1: YAML → 構成図（〜90 秒）

### セリフ

> 「まず一番基本的な機能から。
> 7 ノードのスモールトポロジを用意しました。
> router・firewall・スイッチ・サーバが YAML に書いてあります。
> これを d2v に渡してみます。」

```
uv run python demo.py --scene 1 --open
```

> ★ **Enter を押す**。進捗バーが動き始めたら:

> 「LLM が Graphviz の DOT コードを生成して、Graphviz で描画し、
> 評価モデルがスコアを付けて返してきます。」

> （Iteration 1 のスコアパネルが出たら）

> 「スコアが 9 / 10 出ました。高いですが、評価モデルが
> *まだラベルが揃っていない・LAG の表現が曖昧* と指摘しているので
> 改善を続けます。」

> （Iteration 2、スコア 8 が出たら）

> 「一度スコアが下がりました。LLM が直そうとして別の問題を作ってしまった。
> これも現実です。でも諦めません。」

> （Iteration 3、スコア 9 に戻り「生成完了」が出たら）

> 「最終的にベストの Iteration 1 の図が採用されました。
> 画像を見てみましょう。」

> ★ `--open` で自動的に画像ビューアが開く（または `xdg-open demo/cache/scene1_small/best.png`）

> 「ゾーンが色分けされ、インターフェース名と IP が記載された
> 構成図が出来上がりました。YAML を書くだけです。」

### fallback（LLM が遅い場合）

* live モードで LLM が 30 秒以上かかるようなら:
  > 「LLM の応答を待っています。
  > こういう場合に備えてキャッシュ済みの結果もあるので、
  > playback で続きを見せます。」
  * `Ctrl+C` → `uv run python demo.py --scene 1` で playback に切り替え。

## Act 2: スケール（〜60 秒）

### セリフ

> 「次に規模を上げてみます。
> 73 ノード、10 ゾーンの企業ネットワークです。」

```
uv run python demo.py --scene 2 --open
```

> ★ **Enter を押す**。ゾーン名が順に ✓ になっていくのを見せる。

> 「ノード数が閾値を超えると、d2v は自動でゾーン単位に分割します。
> 全体俯瞰図を 1 枚、各ゾーンの詳細図を 10 枚、合計 11 枚を生成します。
> 人が何百ものアイコンを配置する必要はありません。」

> （完了パネルが出たら `--open` で俯瞰図が開く）

> 「これが俯瞰図です。クリックするとゾーン詳細に展開できます。」

> ★ 画像ビューアで `zone-dc-fabric.png` も開いて見せると◎。

## Act 4-1: validate（設計バグ発見）（〜45 秒）

```

```

> ★ **Enter を押す**。検証結果が 1 行ずつ出てくるのを見せる。

> （❌ ip-address-overlap が出たら）

> 「IP アドレスの重複を検出しました。
> これは実際の設計現場でよくあるミスです。」

> （⚠ spof-device が出たら）

> 「単一障害点の検出です。
> fw-01 や core-sw-01 が落ちたら、どこが切れるかを算出しています。
> LLM は不要です——グラフ理論の決定論的アルゴリズムで動いています。」

> （結果パネルが出たら）

> 「error 1 件、warning 9 件。本番投入前に気付けました。」

## 想定 Q&A

| 質問 | 回答 |
|------|------|
| どの LLM を使っていますか？ | OpenAI GPT-4o または Claude が推奨。Ollama でローカル実行も可能です。モデルは `.env` で切り替えます。 |
| スコアが一度下がりましたが、プロダクションで使えますか？ | ベストスコアの結果を採用するので最終出力は劣化しません。patience パラメータで「N 回改善しなければ打ち切り」を設定できます。 |
| YANG スキーマはカスタマイズできますか？ | `yang/iida-network-model.yang` を拡張すれば対応できます。 |
| validate の検出ルールは追加できますか？ | `src/d2v/validator.py` にルール関数を追加するだけです。プラグイン構造です。 |
| diff は複数ファイルに対応していますか？ | 2 ファイル比較（before/after）が基本です。連続変更は before を前回の after に更新して再実行します。 |
| 既存の NMS/CMDB と連携できますか？ | YAML さえ出力できれば連携可能です。REST API 呼び出しで YAML を組み立てる薄いアダプタを書くイメージです。 |
